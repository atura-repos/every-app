# Maester-dashboard (Atura pilot)

Read-only EveryApp-managed app with private scheduled GitHub App reconciliation every six hours. No public routes, scan trigger, report download, PDF release or automatic email. No customer data or historical JSON is bundled. GitHub artifacts expire after ~14 days. `REPORTS` contains only checked normalized projections; it is **not** accessible by a download route. Original HTML/Markdown is never imported or exposed.

## Security boundary

- Gateway authentication **and a narrow, explicit app grant** are prerequisites. Do not give this app an everyone/org-wide grant. Verify the actual Entra sign-in and direct-URL denial for another member before release.
- Every read checks the SDK-signed `context.user`: exact email `mvanfalier@atura.nl`, required `PILOT_USER_ID`, required `PILOT_ORG_ID`, `web` channel, actor equals user, and an explicit `(tenant_id, org_id, user_id)` row in this app's own D1. Missing settings or grant fail closed. No browser cache of private results; user-provided tenant and suite are validated server-side. The pilot's immutable Gateway user and organization IDs must be determined by an authorized operator and supplied as app secrets, not guessed from email. Neither secrets nor access rows are seeded by this source tree.
- The app has its **own** D1 `DB` and R2 `REPORTS`, never Gateway D1. No public webhook/health endpoint, no tools. An operator must provision `github_sources` rows with an immutable repository ID, installation ID, owner/repo, numeric workflow ID, exact `refs/heads/...`, artifact prefix (`maester-atura-dashboard`, `maester-atura-cis-graph-dashboard`, `maester-atura-cis-exo-dashboard`, `maester-atura-cis-teams-dashboard`) and `enabled=1`. No source or tenant is seeded. Provision the GitHub App with Metadata and Actions **read-only**, install only on approved private repos; set `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` as app secrets (never commit them). Reconciliation creates a five-minute App JWT and requests an installation token scoped to the one registered repository and read permissions. Rotate the key via app secret; no PAT or public route is required.
- Only the matching `dashboard-result-v1.json` from the run-ID-named dashboard artifact is parsed. Six exact top-level keys, strict test-ID/result allowlist, no titles, no error records or evidence; titles in D1 are derived from the test ID. Unknown fields, bad tenant/scope, extra ZIP entries, oversized ZIP/decompression and mismatched repository fail closed. Missing projection records `projection_missing` in `import_events` without ingesting legacy HTML. Artifact projection is read back from R2 by digest and indexed in D1 under a unique repo/run/attempt/artifact key. Retention deletes R2 and D1 rows after one year from scan creation, then records an audit event. The UI does not yet display import events.
- The read model supports schema_version 1: `tenant_id`, `expected_test_ids`, control `test_id`, `title`, `result` (Passed/Failed/Skipped/NotRun/Error). Scan status and workflow conclusion are separate. Missing controls count as skipped except a crashed scan, when they count as technical. Comparison requires same tenant/suite/benchmark/expected ID set and unchanged title per ID; technical scans are not comparable. Titles are a conservative proxy for meaning; an importer must bind semantic definition/version before customer use.
- Do not release customer reports: PDF approval, original-HTML download/isolation, backup retention and live D1/R2/GitHub verification remain outstanding. Reconciliation examines at most 100 recent completed runs and 100 artifacts per run per registered source (20 sources maximum); older/backlogged runs need a separately reviewed backfill. Rerun artifact-attempt binding and semantic benchmark/version metadata are not yet present in exporter v1; do not use repeated attempts for customer reporting until the contract carries attempt/version. The UI states no client version is available. No customer onboarding or production pilot is authorized by this code alone.
